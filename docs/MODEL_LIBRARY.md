# Model library and Kmic profiles

The dashboard lists files found in existing `LAB_MODEL_ROOTS` and models approved in the host agent catalog. Scanned files have unverified engine compatibility. Catalog entries declare model identity, quantization, exact artifact bytes and checksum, supported limits and a tested starting point. Availability checks the approved path, regular file, readability and expected length. The administrator verifies the actual artifact checksum and provenance before admission. A model can appear in both sources.

## Dashboard workflow

1. Select an engine and an approved model. Kmic offers the existing 27B and [Flash Next Fast, Reasoning and 256K profiles](FLASH_NEXT_PROFILES.md). Fixed service profiles show their configured context, gateway alias and capabilities. Start those profiles from **Engine services**.
2. Edit context, batch and microbatch tokens or load a saved preset. The dashboard and backend enforce absolute limits, model-specific ceilings and microbatch ≤ batch ≤ context. The host agent independently enforces those constraints for every staging request. The operator must establish the model-specific ceilings for this build and host.
3. Give the settings a name and optionally mark them as the model default. Selecting the model loads the matching default in the editor. Saved defaults are editor preferences and have no effect on the host until explicitly configured. To revise a preset, load it and save the edited settings under a new name. Use **Set as default** to change the default for existing presets.
4. If changing a running service, use **Stop** and confirm the interruption. Wait for Kmic to be inactive, then choose **Configure next start** and confirm the model and values. Use the existing **Start** control when ready. Staging does not call any systemd mutation or toggle boot enablement. An already enabled unit uses the staged profile at its next normal boot. The engine card shows the reported model alias, the persisted next-start model and settings, and readiness independently. Kmic does not report the live startup parameters through this integration.

A preset can carry optional operator-reported evidence, including a benchmark report SHA-256, prefill or decode tokens/s, and the workload description. Include prompt/output token counts, concurrency, and any relevant prompt/cache behavior in the workload. SQLite retains those fields and the run setting associations available at entry time: engine version, GPU model and count, quantization, exact artifact identity and context/batch/microbatch settings. Attach evidence only if the report matches those settings and environment. Evidence is visible separately from user-saved defaults. The lab does not verify external reports, rank results or mark a preset best. Presets from a changed catalog environment are flagged and do not auto-load as defaults.

## Optional host setup after review

The currently deployed static unit and agent configuration remain supported. Catalog/profile staging requires a separately approved maintenance window and the following review:

1. Back up the sealed agent configuration and native unit, record boot enablement, and review the actual fixed Kmic command and guards. Populate the optional `managed_models` object in the root-owned agent configuration using [the catalog example](../deploy/engine-agent/managed-models.example.json). Keep the existing top-level keys. Use immutable versioned IDs and unique stable served aliases. For the existing model, use the existing served alias and the current context/batch/microbatch settings as the initial values. Register only complete existing files with reviewed content, size, path and per-model bounds. No download is initiated by the library.
2. Use the reviewed agent build and the example `StateDirectory` configuration. The agent writes only the fixed `/var/lib/p100-lab-engine-agent/selection.env` in its private state directory. The file contains the approved model path/alias and three bounded integers, with no keys or other credentials. It is replaced atomically with mode 0600. The API container does not mount this directory or the model paths.
3. Adapt the original **fragment** for `kmic-qwen27b.service`. Keep the existing executable, listeners, API key file, resource and power guards, boot linkage and other fixed flags. Add the required `EnvironmentFile=/var/lib/p100-lab-engine-agent/selection.env` under `[Service]`. Use the following literal single-argument substitutions at the existing model, alias, context, batch and microbatch flags in the native command. Ensure each of these options is present only once.

   ```ini
   # Fragment excerpt. Keep the existing absolute executable and all other reviewed arguments.
   EnvironmentFile=/var/lib/p100-lab-engine-agent/selection.env
   # ExecStart arguments: -m ${LAB_MODEL} --alias ${LAB_ALIAS} -c ${LAB_CONTEXT} -b ${LAB_BATCH} -ub ${LAB_UBATCH}
   ```

   Systemd reads the environment file when launching the service and the braced substitutions each supply one argument to the executable. Review every directive that can override these values. The new fragment and exact digest must be reviewed together. The agent refuses drop-ins, mismatched fragments, digest changes and a managed unit needing daemon reload. [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html) · [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)
4. With approved interruption, stop the service and wait until all jobs finish. Reload the reviewed native fragment in the existing user manager and start the updated agent with the new pin. While the service is inactive, stage the original model with its existing settings **before the first start or reboot**. The required environment file is absent until the first successful stage. Arrange this migration inside the maintenance window, with rollback available if the approved profile is unavailable. Stage/start through the dashboard and verify the native model alias, readiness, and original boot setting. For rollback restore the prior unit and sealed agent config/code, reload the user manager, and verify original readiness and boot setting.

The agent serializes dashboard mutations and rejects staging when the native service is active, transitioning, or has a visible job. Independent local systemd commands and other launchers are outside this lock. Coordinate operator activity during configuration. Dashboard starts retain the existing two-GPU free-memory/utilization/temperature preflight. Boot and independent starts retain the native unit's controls. Same-UID host processes and the administrator remain trusted.

Further work can link imported benchmark evidence with exact profile and artifact identity, compare only equivalent workloads and show verified recommendations, review additional engine adapters, and design an explicit download approval flow with pinned source and exact total size. Production acceptance of the optional unit, readiness after startup, and rollback require a scheduled host window.
