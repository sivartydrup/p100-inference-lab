# Security and planned control boundary

The [measured-history importer](docs/MEASURED_HISTORY.md) is a local operator command, not a web upload/execute endpoint. Its strict bounded schema and converter reject ambiguous, inconsistent and non-finite evidence, strip paths/argv/content/credentials, recompute summaries and append only terminal records. These are operator assertions identified by hashes, not authenticated hardware attestations. The API reads a separately published native snapshot through an optional read-only mount, with no source-database write access. All existing bearer authentication and disabled management routes remain in force. No runner is enabled and no driver, power or boot service is changed by import/publish. The existing unpatched picomatch build-tool advisory remains a visible blocking audit check; it is documented in the guide rather than suppressed.

All `/api/*` routes require a randomly generated bearer token (at least 32 characters). `/healthz` and static UI assets are public. Authentication uses constant-time comparison; no browser cookies or CORS are enabled. Token stays only in React memory and clears on reload/disconnect. API responses disable caching. Never put credentials in URLs, source control, browser storage or frontend build variables. Rotate the token file and recreate the container; open tabs must reconnect with the new token.

The requested http://192.168.0.188:3000 endpoint is for a trusted isolated LAN only. HTTP does not encrypt credentials or history. Use the SSH tunnel or an HTTPS gateway described in INSTALL for untrusted networks. There is no internet exposure configured. Authentication is mandatory even on the LAN. A shared token currently permits history writes as well as reads; it has no host management capability. Rate limiting, individual users and roles are future work.

## Phase 1 boundary

No engine/model control is implemented. The reserved typed control route returns 403 even if LAB_ENABLE_CONTROLS is set. No process startup on app boot, downloads, shell interpretation, arbitrary command/executable/URL/unit/preset input, Docker socket, sudo or host service bus mount exists. The only subprocess calls are fixed argument arrays for read-only nvidia-smi and native user-service status. Native services remain outside Docker; Netdata and SSH are independent.

Container runs UID 10001 with no capabilities, no-new-privileges, read-only root and writable data/tmp only. Host proc read-only mount and optional NVIDIA utility devices expose host metadata, so a compromised container remains a risk; this is not a sandbox for untrusted code. Container secret files are local bind mounts, not an encrypted secret vault. Trusted local accounts/filesystems required; inventory symlink avoidance is not protection against concurrent malicious path replacement.

## Fixture job permissions and isolation

Phase 2 adds only deterministic fixture jobs. All reads require the existing LAB_API_TOKEN bearer credential; the legacy manual benchmark write permission remains unchanged. Fixture submission/cancellation additionally require a separate X-Lab-Job-Token header matching LAB_JOB_TOKEN (or its file). Fixtures must be explicitly enabled and startup rejects a job token shorter than 32 characters or equal to the viewer token. Both credentials are tab-memory-only; jobs, events, exports and logs exclude them. HTTP still exposes both to network observers: use the trusted isolated LAN or an encrypted tunnel/HTTPS.

Job payloads accept only two fixed synthetic preset IDs and bounded trial/warmup/timeout settings. No browser-supplied engine path, model path, command, URL, prompt, plugin or shell flag is accepted. Twenty pending/running jobs are allowed per database; list/detail sizes are bounded. UUID idempotency keys prevent duplicate submissions on retry; reusing a key with a different payload returns 409. Queue admission and state transitions use SQLite transactions; cancellation/completion races cannot commit a successful summary after a committed cancellation request. Events identify a shared job capability, not individual users, and are not tamper-proof against local DB writers.

The API never runs jobs. A separately started worker holds an OS lock on the same local volume as SQLite; only one worker can run per database. The provided opt-in Compose worker has no network, GPU, model mount, host proc mount, secrets or published port, runs UID 10001 with dropped capabilities and a read-only root. It can only generate fixture data and write the shared database. This remains trusted software with DB write access, not an untrusted-code sandbox. Use a local filesystem; network volumes and bypassing the provided lock are unsupported. Native engine/model controls stay disabled regardless of fixture settings.

Worker deadlines/cancellation are cooperative between short bounded fixture steps. SIGTERM marks an active fixture interrupted; after a hard crash the next exclusive worker marks orphaned running jobs interrupted and preserves partial samples. Queued jobs remain queued; interrupted work is never replayed automatically. A request may already be queued when a browser times out/disconnects; retry the same request ID or inspect history before submitting anew. Browser reload clears its pending retry ID and credentials.

## Proposed narrow control layer (not implemented)

The optional [native microbenchmark CLI](docs/NATIVE_RUNNER.md) implements a narrower local-administrator operation, separate from this proposed remote layer. It has no listener or web execution permission. Three opt-in gates, trusted administrator manifests, artifact hashes, fixed argv/environment, resource preflight, per-user worker exclusion and attested bounded systemd units apply. Unconfirmed cleanup blocks the queue. The API opens only an explicitly configured separate history database read-only; native submission/cancellation always return 403. No native executable is launched by API startup. Host acceptance must verify cgroups/user-namespace policy before enabling real jobs. Cooperative GPU preflight cannot exclude unrelated tools/accounts. The detailed guide documents filesystem trust and measurement limits.

Before adding controls, verify actual Kmic/PXA/qr0n sources, licenses, binaries, launch commands and existing process ownership. Keep the web API unprivileged and separate from a dedicated native host agent. The host agent accepts a versioned schema over a local Unix socket with restrictive permissions; no LAN listener. A per-operation capability and authenticated, authorized administrator request are mandatory; do not reuse a read-only viewer credential.

Allow only a finite set of operations (start/stop, load/unload) against administrator-authored engine IDs, fixed service units and immutable preset/model IDs. Resolve IDs server-side to verified absolute paths; never accept shell strings, arbitrary flags, paths, service names or URLs. Use a single job queue, durable audit intent/outcomes, timeouts, idempotency and observed completion. Enforce GPU ownership/memory preflight, mutually exclusive engine scheduling and cancellation semantics. Require explicit user confirmation before interrupting active inference. Audit authenticated actor, preset hash, request ID and result, without credentials or prompts.

Ship only after HTTPS or a protected tunnel, separated read/control permissions, replay/CSRF review, credential rotation, audit integrity, host agent permission isolation and negative security tests are in place. Model downloads need a separate license/provenance and integrity design. No general shell endpoint at any phase.

Report suspected vulnerabilities privately to the repository owner through their published contact. Do not post secrets, private filesystem paths or working exploits in public issues.
